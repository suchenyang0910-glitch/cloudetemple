## 一人公司检查

### AI 是主要生产力

- [假设] 复用当前 `admin-ui` 单页、`/admin/*` 接口路由、现有家族/墓碑存储、匿名日汇总和 Cloudflare Access。只为 moderation、封禁/申诉、数据请求和订单增加必要的服务端接口与表；不另起后台框架，不把内容审核再做成一套通用 CMS。
- [假设] 萌宠园第 1 期的最小后台：机审/举报队列、单条下架与恢复、申诉、封禁/解封、理由和审计；运营只需一名管理员处理例外。预估 AI 辅助开发 5–8 工程日，另加 2–4 日授权/滥用/恢复验收，未含政策和法律审核。
- [假设] 用户模块最小版：默认打码列表、用户来源与牌位条数、按请求导出/删除、封禁/解封。预估 3–5 工程日，另加隐私/权限验收。
- [假设] 订单最小版先定表、状态机、管理列表和核对导出；待收款主体、支付渠道、货币、退款政策明确并获用户批准后才接支付。预估 5–8 工程日，未含支付商、会计核对与本地法务时间。
- [假设] 数据最小版复用同意状态和现有日汇总，增量事件只回答已确认的指标问题；预估 3–5 工程日，另加匿名化和退出验证。所有工期是粗估，未由实施者评审。

### 情感细分、自带传播

- [假设] 分享时刻为主人完成一块宠物纪念碑后，自愿分享不含姓名、碑面私密文字或账户标识的卡片/邀请链接；陌生访客看到的页面不显示虚构墓碑、访问人数或评价。
- [假设] 萌宠园审核指标：①举报在 24 小时内有明确处理结果的比例 ≥90%（每周 ≤30 件，首月不少于 20 件）；②申诉改判比例 ≤10%（少于 20 件时只报告数量，不下结论）；③非授权读取仅邀请可见文字事件为 0。未达标时先缩小公开发布面、修正规则；隐私事件立即停开放并升级用户处理。
- [假设] 订单指标：①支付渠道回调与内部订单的金额/币种/状态日对账匹配率 ≥99.5%；②退款操作 100% 有理由和审计；③未能解释的差异为 0 才允许扩大订单量。任一不达标暂停新收款，保留用户查询与人工退款处理。
- [假设] 数据指标：①同意用户的必需事件完整率 ≥95%；②所有报表分组至少 5 个不同主体，否则合并或抑制；③退出后不再新增该用户事件，历史原始身份映射按政策删除。未达标先修埋点/分组，不以补造数据填空。

### 轻量化、单人可运营

- [假设] 每日最多 20 分钟看待处理举报/申诉和告警；每周最多 30 分钟抽查误拦、访问日志、删除请求和订单差异。举报量连续一周超过单人可在 30 分钟内处理的能力时，系统应限速并暂缓新公开内容发布，优先处理严重项；是否启用自动暂缓规则由用户决定。
- [假设] 机审仅做拦截建议/隔离，不对私密内容做默认扫描或自动删除；批量去重、举报速率限制、告警和每日备份自动执行。退款、删除/导出请求的例外判断、申诉和私密内容投诉仍需人工，不能假设机审消除这些工作。
- [假设] 复用现有主机、数据库、Cloudflare Access、邮件服务和日志，不增加第三方审核/支付服务。小规模试运营的增量服务费估为 US$0/月（前提：用量仍在现有套餐内）；本项目当前月账单、供应商、套餐余量未核实，真实总成本未知。新增付费 AI 审核或支付服务要先有报价并由用户批准。
- [假设] 无实物、仓储、物流或线下场地。用户量增加时先用静态资源 CDN、队列限长、按账号/IP 限速、数据库连接上限和只读汇总缓存；写入请求使用幂等键，积压时显示可重试状态，不无限重试或丢弃审计。

- [已验证事实] 当前 `admin_audit` 字段只有 `at`、`email`、`action`、`object_type`；通过 Access 验证的 summary 与 presale GET 会写入，拒绝/无权限请求没有此处审计。没有目标记录 ID、理由、变更前后值、请求结果或二次确认字段，因为现有后台没有管理写操作。
- [已验证事实] `metrics-store.cleanup()` 会删除 365 天以前的审计记录。当前代码未证明日志具备不可修改/不可删除保证；不能把“写过审计行”说成“不可改审计日志”。

## 2. 用户模块

### 2.1 列表字段和个人信息

- [用户决定] 用户列表可显示用户总数、新增、活跃、来源（Telegram、未绑定浏览器、邮箱、Google）、用户创建的墓碑条数、是否有付款；来源缺失时显示“未知”，不从 IP/设备指纹推断。
- [用户决定] 默认列表不显示真实姓名、完整邮箱/Telegram 号、家族牌位内容、忌日、邀请链接或任何祖先资料。邮件默认保留前两位与域名；Telegram 标识只显示末尾几位，其余掩码。浏览器匿名身份只显示内部随机 ID。
- [用户决定] 家族牌位文字、姓名、图像、供奉内容和成员详情在后台永远不可见；管理统计只显示总条数。用户信息中的“墓碑数”只做计数，不展开碑面或仅邀请可见内容。
- [假设] 活跃/来源指标只对同意统计的用户计算；用户管理所需账户状态、登录方式、封禁状态与处理用户请求所需的最少身份字段作为服务数据另行限定权限，不能将其混进同意统计分母。
- [用户决定] 需要看完整联系方式的例外（例如核实数据导出/删除请求）需再点击、填理由并单独留审计；每次只解封一个字段/一个目标，操作完成后自动重新打码。
- [假设] 用户模块指标：默认掩码字段/权限检查通过率 100%（至少 20 个合成账号）；未经授权信息展示为 0；导出/删除流程审计覆盖率 100%。任一失败即不开放该用户动作。

## 3. 订单模块

### 3.1 订单数据结构

- [假设] 每单字段：内部订单 ID、匿名用户 ID、商品类型、墓碑/独立墓地位置 ID、创建时间、币种、标价/折扣/实收金额、状态、支付截止、支付成功时间、服务开始/到期时间、宽限结束时间、已退金额、支付渠道占位、外部交易 ID、退款/支付事件幂等 ID、最后核对时间。暂不保存银行卡/钱包凭据、Cookie、token 或不必要的收货资料。
- [已验证事实] 当前 staging 代码有台历预订/意向读取，不等于可复用的在线订单或支付系统；本次未发现已接通的支付渠道。支付渠道与收款主体在此留空。
- [用户决定] 商品可关联某块宠物墓碑或一处独立墓地；订单不得带出家族牌位正文。支付接通前订单和收款功能保持关闭。

### 3.2 状态机和期限显示

[假设] 订单状态转换方案：

```text
待支付 ──支付核验成功──> 已支付 ──服务到期──> 宽限中 ──宽限结束──> 已到期
   └────支付超时────────> 已到期
已支付/宽限中 ──获批退款并核对回执──> 已退款（终态）
```

- [假设] “已支付”同时保存支付完成和服务到期时间；“宽限中”仅用于周期服务，是否继续展示墓碑、宽限天数及续费入口都要用户确认。宽限结束后状态为“已到期”；不可把“待支付”当成已收款。
- [假设] 管理列表显示状态、剩余时间/到期日、商品 ID 和异常标记；到期/宽限提示只针对该笔订单，不向其他用户公开用户、墓碑或购买数量。具体宽限长度、提醒次数、价格与周期由用户定。
- [假设] 支付成功只以服务端验签后的支付通知/主动核对为准；通知必须幂等。浏览器返回成功页、截图或管理员手工改状态都不能单独证明到账。

### 3.3 退款与对账

- [用户决定] 退款为管理写操作，仅收款接通后开放；操作前必填理由、二次确认，并通过原支付渠道处理。保留外部退款编号、金额、币种、状态、执行人和结果；退款失败不标“已退款”。
- [假设] 初版只支持全额退款；部分退款、自动退款和跨渠道退款等到支付/会计方案确认后再决定。已发起退款到渠道最终回执前显示处理中，不重复提交。
- [假设] 对账导出按日期范围导出订单 ID、商品类型/ID、金额/币种、订单状态、渠道交易/退款 ID、关键时间和核对差异；不带完整联系方式。导出需二次确认、理由和审计，一次性下载链接 1 小时失效，服务器不保留副本。
- [用户决定] 未确认的收款主体、渠道、银行账户、币种、退款权利/期限、税票/收据规则、墓园租期/续费与宽限长度都是上线阻塞项。现在不配置或接入任何支付方式。

## 4. 萌宠园内容审核

### 4.1 队列与动作

- [假设] 一个队列包含：机审隔离项、用户举报、已下架项、申诉。最小字段仅为内容匿名 ID、公开/仅邀请范围、风险类别、提交时间、举报次数、处理状态和可访问的必要证据；默认列表不载入碑面正文。
- [假设] 状态：`待机审` → `待人工` → `已发布` / `已下架`；任何下架项可 `申诉中` → `恢复` 或 `维持下架`。理由必填，所有决定可回看但不可覆盖旧决定。
- [用户决定] 管理员只能下架/恢复用户内容，不能改写用户文字、替用户立碑或代替用户上供。封禁账号须独立动作并说明理由。
- [假设] 机审负责高风险词/垃圾提交隔离、重复合并和队列排序，不自动永久删除；无命中或不确定项由人工按规则处理。恶意举报限速并允许申诉。

### 4.2 举报指向仅邀请可见内容时

- [用户决定] 审核员可以查看确实对外公开的碑面文字，仅用于处理该条内容的机审、举报或申诉；不能按用户/家庭浏览无关内容。仅邀请可见文字始终默认不可见。
- [用户决定] 审核员平时看不到任何仅邀请可见的文字。
- [假设] 处理“举报本身就是仅邀请可见的文字”有两种政策，待用户定：
  1. **严格不可读**：后台只看到匿名内容 ID、举报类别和举报人提供的说明；不向审核员展示原文字。隐私最强，但有些举报无法核实。
  2. **逐条例外查看**：只允许负责处理此举报的单邮箱管理员打开被举报的那一段；必须写案由、二次确认，临时授权自动失效；审计记录谁在何时查看哪一条及处理结果。不得浏览同一家庭其他文字或牌位。
- [假设] 选择第二种时，受限审核员角色仍不能打开私密文字；仅管理员可处理例外。若需多人复核，先由用户批准合规的第二审核人和权限，不默认扩展白名单。

### 4.3 角色

- [用户决定] 管理白名单暂时仍只有一个邮箱；`admin-emails.txt` 保持一个。以后可设计审核员角色，但启用由用户另行批准。
- [假设] 主管理员拥有用户请求、封禁、订单/退款（支付接通后）及私密内容举报例外查看权限；审核员仅能处理内容队列、下架/恢复和申诉，看不到用户列表、订单、完整联系方式、家族牌位内容或导出功能。

## 5. 数据模块

- [用户决定] 报表只使用已同意统计的那部分用户；每张报表显示“同意统计的用户”口径、时间窗、事件定义和样本不足说明。拒绝同意或撤回后，不再新增其分析事件。
- [假设] 指标：①访客与 1/7/30 日回访；②上香、礼拜、静坐、木鱼、念珠五项开始/完成次数；③萌宠园立碑、公开献花动作数；④收款接通后订单支付/退款转化；⑤粗粒度设备类别和进入渠道（Telegram / 浏览器 / 其他）。支付未接通时转化显示“未采集/未接通”，不显示估算收入。
- [假设] 事件只存日、事件名、必要类别和计数；不带姓名、邮箱、电话、完整 IP、牌位 ID、墓碑正文、精确地理位置或可跨站追踪的设备指纹。设备仅归并手机/桌面/未知，渠道只保留上述粗类。
- [假设] 以 ≥5 个独立同意主体作为最小展示门槛；低于门槛隐藏或并入“其他”。禁止导出用户级事件行、可反查时间序列或匿名传播关系边。每个指标仅由预先定义的聚合查询产生。
- [假设] 同意记录只保存策略版本和同意/撤回时间；撤回后删除可识别映射和未聚合事件。已不可逆聚合且无法回溯个人的数据是否保留，交由隐私政策确认。

## 6. 既有规则及已拍板调整

- [用户决定] **后台只读 → 指定写操作。** 第二期开放范围仅为：封禁/解封账号、下架/恢复内容、处理举报与申诉、收款接通后的退款、应请求导出/删除数据。每项必填理由并写入不可修改的审计日志。除此之外继续只读；不修改用户正文，不替用户立碑或上供。
- [用户决定] **不含个人数据 → 有限受控显示。** 用户列表和订单允许必要个人字段默认打码；需看完整信息时二次点击、填理由、留审计。家族牌位内容永远不可见，只显示条数。
- [用户决定] **单邮箱白名单 → 暂不扩展。** 继续由唯一白名单邮箱管理员操作；审核员只作为未来选项，单独批准后才能启用，且只能访问内容审核。
- [已验证事实] 当前第一期保护列表已经是管理员主动查看联系方式并留访问审计的例外；以上已拍板规则应写进二期授权和用户界面，不应误称为当前已实现。

## 7. 安全、审计与导出

- [用户决定] 后台仍走 Cloudflare Access；服务端验证 Access assertion，并以唯一 `ADMIN_EMAILS` 白名单限制管理员。不得只在浏览器隐藏按钮来保护权限。
- [用户决定] 每个写操作都要二次确认并填写理由；所有成功/失败尝试、敏感信息解封、导出、删除、退款、下架/恢复都留不可修改审计。日志不能含验证码、Cookie、token、完整 IP、碑文或家族牌位正文。
- [假设] 写接口只用 POST/DELETE 等非 GET 方法，校验会话、角色、CSRF、防重幂等键和目标权限；成功写入与审计写入在同一事务提交。操作前展示目标和影响范围，用户确认后再提交。
- [假设] 为满足不可修改要求，把审计写入与管理员数据库角色隔离：管理员应用账号只有 INSERT/SELECT 权限，禁止 UPDATE/DELETE；每日将签名摘要副本送入有保留锁的只追加存储。保留期限、存储供应商和成本待安全/法律复核。当前 P1 审计表不满足此设计。
- [假设] CSV/JSON 导出经服务端字段白名单生成，一次性 URL 1 小时到期，禁用缓存与搜索索引；下载和过期清理都留审计。后台服务端不落长期副本；管理者需按内部设备策略删除本地下载。
- [用户决定] 后台页面/API 不显示验证码、Cookie、token 或完整 IP；日志与报表默认不显示完整邮箱、Telegram 号或真实姓名。

## 9. 正式后台开启条件

- [用户决定] 正式环境后台何时开启由用户另行批准；本文不改 `ADMIN_ENABLED`、白名单或生产配置。
